# TS7 DSH Remote — 项目分析（2026-11-16）

状态事实见 [STATUS-2026-11-16.md](STATUS-2026-11-16.md)。这里只做判断：这个项目成熟到什么程度、哪些设计真的对、风险在哪、下一步该往哪投。

## 一、总体判断

**产品成熟度明显高于工程成熟度，这是项目当前唯一的结构性矛盾。**

- 产品侧：16 个版本、11 篇 release note、真机与 MuMu 端到端跑通，功能已覆盖"用手机完整驱动 DSH"这件事的全部主路径（发现、配对、多主机、审批、计划、图片、归档、协作、日志）。
- 工程侧：无 CI、101 个测试未入库、插件包落后源码、tag 停在 v0.8.4、分发元数据指 0.8.3。

这不是能力问题，是节奏问题：19 天内 25 次提交、16 个版本，平均 1.2 天一个版本，全部由单人完成。快速迭代把功能推到位，也把"可交付性"留在了最后。当下边际收益最高的动作是收口，不是加功能。

## 二、设计上做对的四件事

**1. 不自造协议。** 手机端不实现 DSH 的 Typert，只用精简 JSON + SSE，所以 Android 侧是纯手写 Kotlin（8.4k 行），没有代码生成器、没有协议同步负担。代价是宿主 API 变更要手改，但这个代价是可预期、可局部化的。

**2. 双端并发审批，而不是手机代理审批。** 手机建卡的同时把请求交给桌面端，两端各自回答、先答为准；手机先答时 host 下发 `cancel` 帧让桌面撤卡。这一手同时解决了三件事：手机不在线不会卡死、桌面端不必知道手机存在、两端不需要额外的状态同步协议。全项目最漂亮的一处设计，也是 0.8.2 之后几乎没再返工的地方。

**3. 选路分层清晰。** 局域网优先、tailnet 兜底、内嵌 userspace 节点不接管系统网络。PC 端 `tsnode` 与手机端 `gobridge` 两个 tsnet 实现合起来，才让"电脑和手机都可以不装 Tailscale"这个卖点成立，且不与系统 VPN 冲突。

**4. 用降级链代替硬依赖。** 历史读取 `page → events → inspect`、Tailscale 状态目录三级回退、宿主 API 缺失回 501。在一个 API 还在动的宿主上，这个习惯是项目能活下来的原因——0.2.x 的四次破坏性变更全靠这类兜底撑住，而不是靠提前预判。

## 三、结构性风险（按伤到用户的概率排序）

**R-A｜与宿主内部 API 的强耦合，是持续税而非一次性问题。** 插件直接调 `ctx.sessionController`、`ctx.sessions`、`ctx.workspaceRegistry`、`ctx.approval`、`ctx.userQuestions`，`engines.dsh` 锁在 `0.2.1-rc.2 ~ 0.3.0-0`。0.2.x 一次小版本就打破四处：子代理必须用 durable parent 地址、`resolveByPath` 变 async、`settings.plugin.item` 被 `settings.plugins.tab` 取代、`turn/end.reason` 从字符串变成对象。缺的不是兜底（已有），而是**对真实宿主的契约探测**：现在只能等用户报错再手工适配。

**R-B｜单点维护 + 无 CI + 测试不在仓库。** 15k 行、两个平台、零自动化回归。换一台机器 clone 下来，`npm test` 是 0 个用例；README 却写着 101 个通过。这是整套系统里最薄的一层。

**R-C｜交付形态会持续制造支持成本。** debug 签名 APK 60.6 MB（双 ABI，含 15.7 MB gobridge.aar）、应用层明文 HTTP + `usesCleartextTraffic`、token 明文存 SharedPreferences、插件包带 21.3 MB 未签名 exe（安全软件会拦，README 已记）。自己用没问题，给别人用每一条都会变成一轮问答。

**R-D｜复杂度集中在四处大文件，其中一处没有测试。** `server.js`（1,401）+ `client.js`（1,176）占 host 代码 40%；`BridgeRepository.kt`（71 KB）+ `SessionScreen.kt`（46 KB）是 Android 的改动重心。18 个 host 模块里 12 个有测试，唯独 `client.js`（面板 1,176 行）零覆盖——而它恰好被 0.2.x 的插槽变更打破过一次。

**R-E｜发布链路没有人肉之外的自检。** 本次发现 tgz 落后源码，靠的是逐文件比大小；没有哈希门禁。开发态用 junction 直链源码，运行时永远最新，产物是否最新没有任何信号。

## 四、质量评价

- **release note 是这个项目最被低估的资产**：现象 → 根因（引用宿主源码行为）→ 做法 → 文件级变更清单 → 验证方式 → 升级注意。11 篇都是这个结构，等于一部可追溯的决策史。缺的是 README 这道"能力门面"——它落后了 4 组功能，导致外人读到的项目比实际弱。
- **测试布局合理但重心偏移**：`server.test.js` 1,126 行、`approvals` / `collab` / `group` 各 270 行左右，覆盖了最容易出错的并发与权限边界；空白在面板（`client.js`）、装配（`index.js`）、状态（`state.js`）、发现（`discovery.js`）与组内工具（`tool.js`）。
- **代码风格一致**：host 全部 ESM 无构建步骤，中文注释解释"为什么"而不是"是什么"，异常路径基本都有明确的错误码与状态码。这在个人项目里少见。

## 六、投入顺序建议

1. **交付收口**（P0，见状态文档）：测试入库 → 升 0.8.9 → 重打包并做哈希门禁 → 补 release note 与 README → 打 tag、修 contrib。做完这一轮，项目才真正"可分发"。
2. **回归网**：测试入库只是第一步；接一个最小 CI（check + test + 打包哈希比对），才能保证下次宿主升级不靠人肉验证。
3. **宿主契约探针**：把已经在用的降级链升级成启动时自检——探测 `sessionController` 的方法集、`workspaceRegistry.resolveByPath` 是否返回 Promise、`settings.plugins.tab` 是否存在，结果写进面板状态。这样 0.3.x 再来一次破坏性变更，用户看到的是"哪一项不支持"，而不是"手机连不上"。
4. **交付形态**：release 签名 + 按 ABI 拆分或 App Bundle（60 MB → 30 MB 级）、token 进 Keystore。这两项做完，"给别人用"的支持成本会掉一个数量级。
5. **放在最后**：iOS（等于重写网络层与内嵌节点）、手机端取消归档（0.8.8 留下的唯一功能不对称，但影响面小）。

**不建议现在做的**：新功能扩展。功能面已经超出"个人使用"所需，继续加功能只会扩大没有回归网保护的面积。
